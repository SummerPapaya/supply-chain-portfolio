03新候选 N1 · 出口管制与制裁筛查

Candidate N1 · 非 Top 7 缺口，来自雷达热点 + Gartner Trust & Governance

源质量全场最高日更 · 免密钥 · CORS 全开Gartner 未覆盖主题

ScreenLens · 出口管制与制裁清单筛查台

一句话定位：把「这个交易对手、这条船、这家供应商能不能碰」从翻 11 张官方清单，变成一个当日可查、命中即给证据链的筛查动作。

为什么它不是「第二个 TariffLens」

这是它最大的质疑，必须先答。TariffLens 回答的是「要交多少钱」，ScreenLens 回答的是「能不能交易」——前者是税率测算，后者是主体筛查；前者数据是税率表，后者数据是名单；前者的红线是「不做 HS 归类」，后者的红线是「不做法律判定」。两条线在实务里由不同岗位负责，互不替代。

更关键的是它可以做成跨应用的治理层，而不是又一个合规孤岛：CSL 里 1,540 条 Vessel、342 条 Aircraft，正好能对 VeloCortex 的船舶做尽职调查。三个应用由此连成一条链：

三层数据架构

L1
实时层 · 美国 CSL 合并清单 已实测 · 日更
26,144 条，`last-modified` 显示在页面上（如「名单快照 2026-09-29 11:15 GMT，来源 11 张清单」）。可直取或降级为构建期快照；无论哪种，页面必须显示日期。
L2
扩展快照层 · 欧盟清单 / OFAC 直链 构建期预取
欧盟 24.8 MB CSV 与 OFAC SDN 各自落成瘦身 JSON，用于交叉验证「美国清单未命中 ≠ 全球无风险」，页面上分区标注数据源与法域。
L3
演示层 · 筛查样例 标注 DEMO
内置若干公开报道过的典型主体（含船只类型），演示不同清单、不同 programs（如 SDGT / 561-Related）的命中差异与处置路径。全部标 [DEMO]，与用户真实输入分区。

功能模块

  • 批量筛查：粘贴一份对手方清单（供应商 / 客户 / 货代 / 船名），一键出命中表。这是真实工作形态——没人一次只查一个名字。
  • 命中卡：显示命中字段（name / alt_names / address / SWIFT-BIC 等 ids）、所属清单、programs、remarks 原文、source_information_url 官方出处，以及「建议做什么」（进一步尽职调查 / 咨询法律 / 申请许可）。
  • 相似度与匹配依据透明：分数、命中字段、是否仅凭音译别名命中，全部摊开；不隐藏判据。
  • 对象类型分流：Entity 10,341 / Individual 7,652 / Vessel 1,540 / Aircraft 342 四类不同处置剧本——船名查的是船东与 AIS 关联，个人查的是 KYC，性质不同。
  • 可导出筛查记录：时间戳 + 名单版本 + 输入 + 结果，形成一条可审计的决策留痕链（这正好落在 Gartner 的 Decision Governance 上）。

红线（与 TariffLens 同等级别，不可回退）

  • ① 只出「候选命中」，不做法律判定。命中 ≠ 禁止交易。官方口径原话就是「additional due diligence should be conducted before proceeding」——直接引用它，不要自己发明结论。
  • ② 不提供「合规通过」。只能显示「当前名单版本未命中」，并注明这只是筛查链条中的一步；不做任何「可以交易」的表述。
  • ③ 名单版本必须可见。显示 last-modified 与覆盖的清单列表；旧快照要显式标注日期，不用旧名单冒充当日。
  • ④ 不做自动 HS 归类（延续 TariffLens 红线 01）：应用只接受用户给定的主体与商品信息，不给归类建议。

实现要点（33.8 MB 不能直接扔给浏览器）

  • 构建期瘦身：只保留 name / alt_names / addresses.country / source / programs / type / entity_number，预估可压到原始体积的两三成，gzip 后更小。
  • 匹配策略先粗后细：blocking（首字母 + 国家 + 类型）缩小候选集，再对候选做编辑距离 / 音译近似打分。26k 条 × 用户输入的全量相似度会造成明显卡顿。
  • 批量输入要限制单次条数并显示进度，不做「静默等待」。

A 与 N1 的分差只有 0.1，凭什么 A 还是第一

两条都不是数据源问题，而是叙事与版块结构问题：

  • A 落在既有的因果链里：它对应 Top 7 的 #5，版块标题「从研究到产品」的因果关系不变。N1 不在 Top 7 内，若要做，得先补一条「趋势落地」的叙事线（承认 Gartner Trust & Governance 是第二个选人来源），否则它会显得「来路不明」——而补这条线本身是额外工作。
  • A 的业务价值是全榜并列最高（9.5），N1 的 8.5 高但不到顶。
  • N1 会改变版块配比：三个应用里两个合规（TariffLens + ScreenLens）。虽然我给它的解法是「做成跨应用的治理层」（接 VeloCortex 的船），但那是设计意图，读者第一眼看到的仍是「又一个查名单的」。

但反过来说，N1 的落地成本大概率低于 A：没有多源去重、没有地理命中计算，核心只是索引与模糊匹配；数据源也从四源变成一源 + 两个构建期快照，失败面小得多。

修订建议：A → N1 → B（把 ScreenLens 提到 ForecastArena 之前）

Round 2 的排序是 A → B。本轮新增证据后我改口：N1 应该排在 B 之前。理由是 B 的两个短板这轮都没有被解决——仍然没有 SKU 级实时源，「多模型对比」的叙事仍与五份报告重叠；而 N1 的源质量实测是全场最高的一个，上线成本还更低。

B 的独门资产（你的真实 pilot 与那个诚实负结果）不会因为晚做而失效，反而等 A / N1 上线后，可以用它们已经建立的方法论与口径语言来包装——届时它不是「第三个应用」，而是「本站方法论的一次自检」。

如果这条排序你认可，那么接下来的单步动作不变：先确认 A 的第一条红线（不调用 LLM，编排为确定性规则并页面明示）。N1 的红线（只出候选命中、不提供「合规通过」）可以在 A 开工后再定稿。
